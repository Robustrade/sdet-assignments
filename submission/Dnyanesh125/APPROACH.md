# SDET Assignment - Test Strategy & Approach

## 1. Understanding

The system under test is a Subscription & Billing Service.

The automation will validate the subscription lifecycle across multiple
layers instead of validating individual API endpoints in isolation.

The main areas of validation are:

- API behaviour
- Subscription state transitions
- Payment provider interactions
- Webhook processing
- Database persistence
- Idempotency and duplicate delivery
- End-to-end workflow consistency

The primary goal is to verify that the externally visible API behaviour,
business state and persisted data remain consistent throughout the
subscription lifecycle.

---

## 2. Scope

### In Scope

- Subscription creation
- Subscription retrieval
- Subscription cancellation
- Subscription lifecycle transitions
- Payment success and failure scenarios
- Payment provider interaction
- Webhook signature validation
- Duplicate webhook handling
- Out-of-order webhook handling
- Database persistence validation
- API/database consistency
- Invalid state transitions
- Provider call count and arguments

### Out of Scope

- UI testing
- Real payment provider integration
- Performance/load testing
- Production monitoring
- Exhaustive billing features such as taxes and multi-currency
- Full production-grade authentication/authorization

---

## 3. System Under Test Assumptions

A minimal TypeScript/Node.js service fixture will be used to demonstrate
the test strategy where an existing service is not provided.

The fixture will expose the required HTTP APIs and use an embedded or
in-memory persistence layer so that database state can be queried by tests.

The payment provider will be represented by an interface and replaced
with a configurable mock implementation during tests.

---

## 4. Test Levels

The automation will validate the system at the following levels:

### API Level

Validate:

- request validation
- response status codes
- response payloads
- subscription creation
- subscription retrieval
- cancellation
- webhook request handling

### State Machine Level

Validate:

- every supported lifecycle transition
- invalid transitions
- terminal behaviour of canceled subscriptions
- webhook-driven transitions
- protection against invalid/out-of-order state changes

### Persistence Level

Validate:

- subscription state and plan
- invoice/payment records
- processed webhook events
- audit/event history where applicable
- consistency between API state and persisted state

### Integration / Workflow Level

Validate complete business workflows involving:

API → service → payment provider → webhook → database.

---

## 5. Payment Provider Strategy

The payment provider will be abstracted behind a dedicated interface.

A mock payment provider will support configurable outcomes:

- success
- decline
- timeout

The mock will record calls so tests can verify:

- call count
- customer
- payment method
- amount
- billing/reference information

The real payment provider will not be called by the test suite.

---

## 6. Webhook Strategy

Webhook payloads will be generated by test builders and signed using
the expected HMAC mechanism.

The test suite will cover:

- valid signatures
- invalid signatures
- malformed payloads
- duplicate event delivery
- out-of-order events
- events for canceled subscriptions

Webhook event IDs will be used to verify idempotent processing.

---

## 7. Database Validation Strategy

Tests will validate persisted state through repository/DAO abstractions
rather than scattering raw database queries throughout test cases.

The main entities validated will be:

- subscriptions
- invoices/payments
- webhook events
- audit/event history where modeled

Tests will verify that database state matches the API-visible state and
business rules after each important workflow.

Test data will be isolated between scenarios to avoid false positives
caused by stale state.

---

## 8. Required Invariants

The automation will explicitly verify important business invariants,
including:

- A subscription cannot become active without a successful persisted
  payment where payment is required.
- A canceled subscription cannot transition back to another lifecycle
  state.
- Duplicate webhook delivery does not create duplicate payment/invoice
  records.
- A duplicate webhook does not repeat side effects.
- The payment provider is called at most once for a genuine billing
  attempt.
- Replayed webhooks do not trigger new provider charges.
- API-visible subscription state matches persisted subscription state.
- Plan price and trial rules are applied consistently.

---

## 9. Design Patterns

The test solution will use design patterns where they provide a concrete
benefit.

### State Machine

The subscription lifecycle will be represented explicitly so invalid
state transitions are difficult to perform accidentally.

### Builder

Builders will be used for customers, subscriptions and webhook payloads
to keep test scenarios readable and reduce repetitive setup.

### Payment Provider Abstraction

A payment provider interface will create a seam between the service and
the external dependency, allowing a configurable mock provider to be used
in tests.

### Repository

Repositories will encapsulate persistence access and keep database
queries out of individual test scenarios.

---

## 10. Test Data Strategy

Test data will be created using builders and isolated per test scenario.

Tests will avoid depending on records created by other tests.

Plans, customers and payment outcomes will be explicitly controlled by
each scenario where required.

---

## 11. Key Scenarios

The initial automation will cover:

1. Successful subscription creation and activation.
2. Subscription creation with payment failure.
3. Invalid plan/customer/payment method validation.
4. Successful cancellation.
5. Cancellation of an already canceled subscription.
6. Every valid subscription lifecycle transition.
7. Invalid lifecycle transitions.
8. Successful payment webhook.
9. Failed payment webhook.
10. Duplicate webhook delivery.
11. Out-of-order webhook delivery.
12. Invalid webhook signature.
13. Malformed webhook payload.
14. Payment provider success, decline and timeout.
15. Provider call count and argument validation.
16. API/database consistency after lifecycle changes.

---

## 12. Test Architecture

The test solution will separate responsibilities into:

- API client
- test fixtures/environment setup
- domain/state machine
- payment provider mock
- repositories
- test data builders
- assertion/verification helpers
- scenario tests

The objective is to keep test scenarios focused on business intent while
moving transport, persistence and test-data setup into reusable components.

---

## 13. Red / Blue / Green Workflow

Implementation will follow a behavior-first approach:

1. Red - write a failing test for an important behaviour or invariant.
2. Blue - implement the minimum required support code.
3. Green - refactor while keeping the test suite passing.

The final submission will prioritize maintainability and correctness over
framework size.

---

## 14. Technology

- TypeScript
- Playwright Test
- Node.js
- Embedded/in-memory persistence

Playwright will primarily be used for API and workflow automation rather
than browser-based UI testing.

---

## 15. Known Tradeoffs and Limitations

The service fixture will intentionally remain small and focused on the
subscription and billing workflows required by the assignment.

The persistence layer will prioritize deterministic test execution and
easy inspection over production-scale database infrastructure.

Concurrency/racing webhook delivery may be covered as an additional
scenario if time permits, but mandatory lifecycle, idempotency,
persistence and provider interaction scenarios will take priority.

---

## 16. AI Usage

AI tools were used as an assistant during the development process.

All generated suggestions and code will be reviewed, tested and validated
by the candidate. Final architectural decisions, scenario selection,
implementation and verification will be personally reviewed and corrected
where necessary.
